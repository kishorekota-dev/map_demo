# Graph checkpoints and durable recovery

The graph uses the installed LangGraph `BaseCheckpointSaver` contract with a PostgreSQL implementation in production. Development defaults to `MemorySaver`; set `CHECKPOINT_BACKEND=postgres` to exercise restart behavior locally. Production rejects disabled checkpoints and the memory backend. `CHECKPOINT_ENABLED=false` disables graph checkpointing only outside production and therefore disables graph recovery.

The [V2 migration](migrations/V2__servicing_graph_checkpoints.sql) stores typed checkpoint snapshots, metadata, parent links, and pending task writes. Writes use synchronous graph durability: a superstep checkpoint must commit before the next step starts. Pending successful task writes survive an interrupted superstep. Threads are hashes of deployment tenant, customer, session, and execution ID; queries also scope by deployment tenant and graph namespace. Every new workflow gets a new thread, avoiding stale response/confirmation fields from prior workflows.

`CHECKPOINT_DATABASE_URL` selects the database, falling back to `WORKFLOW_DATABASE_URL`, then the service's `DB_*` settings. The same verified TLS settings apply. `CHECKPOINT_SCHEMA_AUTO_MIGRATE=false` verifies the installed schema without DDL; this is the production default. Development defaults to advisory-lock-protected schema creation. Run controlled migrations before production startup. The bundled production profile uses the workflow database for checkpoints; a separately configured checkpoint database needs V2 applied there and a reviewed deployment override. Database failure never switches a durable deployment to memory.

The durable SQL session stores the pinned control-plane snapshot, original interaction ID, and active graph run. Before graph execution it saves the original noncredential input. The customer JWT is excluded from graph channels, checkpoint configuration, input task writes, and that recovery input. Each node receives the current authenticated request credential through asynchronous request-local context. Checkpoints still contain customer conversation, field values, and tool results, so apply the enterprise's database encryption, access, backup, and retention controls.

An interrupted run returns `code: workflow_recovery_required`. The same owner may call `POST /api/orchestrator/session/:sessionId/recover` with a current access JWT and an empty body. The server acquires the existing tenant/session advisory lock, rechecks ownership and expiry, verifies the original thread/interaction/release/channel, and resumes the latest checkpoint. Caller-supplied checkpoint IDs, versions, or replacement inputs are ignored. New messages, feedback, and channel changes stay blocked until recovery completes. The context endpoint exposes only `recoveryRequired`, not checkpoint contents. Operators can inspect context and reconcile uncertain effects but cannot impersonate the customer to resume banking execution.

Recovery is explicitly requested with fresh authentication; there is no background customer-token replay. The customer chat offers **Resume interrupted request**, using an owner-checked adapter that restores chat feedback state. A completed graph with an interrupted terminal session write can finalize from its stored response. Completed prompt replay requires matching unexpired pending feedback, so a later confirmed/cancelled action cannot resurrect an old confirmation. If the first checkpoint never committed, recovery can start the trusted original input: synchronous durability prevents dispatch before that initial checkpoint, and the operation ledger remains authoritative. An expired session or mismatched execution is blocked for investigation.

Graph durability does not replace the [effect ledger](CONTROL-PLANE-RUNTIME.md#concurrency-idempotency-and-uncertain-outcomes). A financial result acknowledged in the ledger is replayed without dispatch. A process killed after dispatch but before acknowledgement requires reconciliation; graph resume never blindly repeats that mutation. Confirmation and data-collection turns continue to use durable SQL feedback/session records; confirmation is deliberately outside the graph and retains its existing ledger protection.

Tests use a disposable PostgreSQL database and real child-process `SIGKILL` crashes around fixture effects. They verify recovery after a committed checkpoint, recovery after ledger success before the next checkpoint, and refusal to redispatch an unacknowledged effect. Active workflow tests also check fresh credentials, pinned identity, pending task writes, and checkpoint credential exclusion. They do not certify a real bank provider's reconciliation behavior. See [runtime validation](CONTROL-PLANE-RUNTIME.md#validation).

This implementation follows the installed saver interface and [LangGraph persistence documentation](https://docs.langchain.com/oss/javascript/langgraph/persistence). There is no public arbitrary time-travel API, automatic cross-release graph migration, or automated checkpoint retention job. Keep active checkpoints and unresolved ledger entries; purge completed histories only under an explicit retention policy. Rolling code upgrades must preserve graph node/channel compatibility for active executions or drain/reconcile those executions first.
